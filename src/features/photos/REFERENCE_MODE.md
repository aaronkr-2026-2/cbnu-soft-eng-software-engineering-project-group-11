# Native iOS Reference imports

Roll imports and single-photo Relink present Apple's `PHPickerViewController`, configured with `PHPickerConfiguration(photoLibrary: .shared())` and `.images`. Multi-selection uses `selectionLimit = 0`; Relink uses 1. iOS owns Photos/Albums navigation, confirmation, localization and appearance; exact tab names and gestures depend on the OS. No custom grid is presented. Legacy bridge label/theme arguments remain accepted but do not customize the system picker.

`.default` prioritizes native selection gestures; `.ordered` is deliberately avoided because Apple documents that it disables swipe-to-select. Gesture behavior still requires verification on the target iOS version. Numbered tap-order selection is not guaranteed; frame order follows the confirmed result array returned by iOS. The provider and Roll store preserve returned order, skip duplicates, and append after existing frames. Cancel returns no selections and makes no archive write.

Persistent references require PhotoKit read access, even though PHPicker alone can export files without that access. Roll Detail explains why access is needed; the provider checks/requests Photos read permission when Add Photos is invoked. Full or Limited permission can proceed. PHPicker selection does not expand Limited PhotoKit access: each selected local identifier is independently verified. Null, inaccessible and invalid identifiers are rejected with an explicit access message. Manage Access uses the limited-library permission picker or Settings, followed by retrying the import. Never persist item-provider URLs or substitute copies. If the FiLog native module is absent, show the native-build-required message; there is no Copy fallback.

Metadata and optional cloud identifiers are mapped off the main thread for all valid selected identifiers, including mixed batches containing nil identifiers. Existing cloud recovery, Retry, Relink and previously saved Copy records remain supported. No original is modified and no permanent full-resolution copy is created during import.

`PhotoReferenceService` is the async resolver. Never display a Reference's legacy thumbnailUri or use it as an export fallback. `resolvePhotoUri` is synchronous compatibility code for Documents Copy records only. Session caches verify availability before reuse, regenerate purged files, coalesce requests and invalidate on AppState/library changes. Native PhotoKit derives appropriately sized temporary JPEG renders, explicitly allows iCloud network access, and never mutates originals. Full resolution is requested for the active Viewer or an explicit share/save operation; contact sheets use bounded 1200px requests.

Viewer contains localized Retry and Relink controls. Limited lookup failure is ambiguous, so it is not called deletion. Denied opens Settings; limited Retry uses `presentPermissionsPicker`. A replacement is verified before writing, with photo/roll identity, ordering and original details preserved. Old picker-URI-only records remain in the archive, unavailable until explicitly relinked.

Cloud-identifier recovery: at import (and on Relink) the native module asks `PHPhotoLibrary.cloudIdentifierMappings(forLocalIdentifiers:)` for each asset's `PHCloudIdentifier` and the provider stores its `stringValue` as optional `cloudIdentifier` when one is returned; an asset without one imports normally. When resolution reports `unavailable` or `limited` and the record has a `cloudIdentifier`, `PhotoReferenceService` calls native `locate`, which uses `localIdentifierMappings(for:)`; not-found and multiple-match results never pick an asset. A mapped identifier is verified independently, then `recoverPhotoReferences` compare-and-sets only `assetId`/`localIdentifier` (and drops a stale `thumbnailUri`) on records still holding the stale identifier; photo IDs, Roll data, order and details are unchanged. Denied permission and temporary errors never trigger a lookup. Each stale reference is looked up at most once until Retry, app activation or a library change. A failed save keeps the on-disk identifiers and shows the photo for that session only. The validator does not inspect `cloudIdentifier`, so an odd value can only disable recovery, never block the archive. This improves, but does not guarantee, recovery after restore or on another iPhone using the same iCloud Photos library.

Copy code remains for compatibility with existing records and tests. A previously saved Copy preference does not enable Copy import in the MVP. Copy paths still resolve relative to Documents; cleanup only deletes correctly owned files after successful persistence and protects shared paths.

See root `RELEASE_READINESS.md` for validation/recovery rules, exact changed files, commands and the mandatory iPhone test matrix. This module requires a rebuilt native app; Expo Go and a Metro reload cannot provide it. No backend, destructive migration, Photos deletion or backup/restore feature is introduced.

## Verification still required on iPhone

Rebuild the native app; Metro reload cannot replace the picker in an already installed binary. Verify Photos/Albums, system language/light/dark appearance, single/multiple/unrestricted selection, confirmation order, cancel and sheet dismissal. Test first-use permission, denial, Full and Limited access (both accessible and outside-selection assets), granting additional access and retrying. Restart to resolve references, remove an original to see unavailable, and test iCloud-only originals with network access and offline retry. Confirm cloud recovery on a second device with the same iCloud library. Automated mocks cannot validate Apple's UI, permissions, iCloud behavior or gestures.
